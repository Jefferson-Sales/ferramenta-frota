# Ferramenta da Frota — contexto do projeto

## O que é

Uma ferramenta web (HTML/JS estático + Supabase como backend) para profissionalizar a gestão da frota da Beep Saúde, substituindo controles que hoje vivem em planilhas Excel/Pipefy/Metabase. Cobre 6 módulos: **Gestão da Frota** (veículos, hubs, contratos), **Manutenções** (ordens de serviço), **Qualidade da Frota** (checklists de veículo e anomalias), **Multas**, **Financeiro** (fornecedores, notas fiscais) e **Carros Elétricos** (recargas, telemetria). Há também um formulário mobile separado, `checklist.html`, que substitui o formulário "Checklist Frota 2026" do Pipefy. Usuário principal: Jefferson Sales (Coordenador de Frota, admin), com acesso ampliado a outras pessoas do time por módulo.

### Problemas de configuração já resolvidos (não repetir)
1. **Link de convite por e-mail quebrado** (apontava pra `localhost`) → corrigir Site URL/Redirect URLs em Authentication → URL Configuration.
2. **"email rate limit exceeded"** ao convidar usuário → plano grátis do Supabase tem limite baixo sem SMTP próprio. Contornado criando usuário direto (Add user → Create new user, com senha e "Auto Confirm User").
3. **Perfil não carregava ("Sem Perfil") mesmo com RLS certo** → faltavam `GRANT` de Postgres pros papéis `anon`/`authenticated` no schema customizado `frota` (schema fora do `public` não recebe isso automaticamente, é independente do RLS). Rodar os `GRANT ... ON SCHEMA frota` / `ALTER DEFAULT PRIVILEGES` se isso voltar a acontecer num schema novo.
4. **`DROP TABLE`/`DROP POLICY` via MCP do Supabase travam** (timeout ~180s) sem motivo aparente — `CREATE`, `ALTER`, `SELECT` funcionam normal. Para redefinir uma policy, usar `ALTER POLICY nome ON tabela USING (...)` em vez de `DROP` + `CREATE`.
5. **Edge Function dava "Failed to fetch" no browser** → `verify_jwt: true` na plataforma bloqueava o preflight CORS (requisição `OPTIONS` sem header `Authorization`). Resolvido com `verify_jwt: false` + validação própria dentro da function.
6. **`frota.checklists` (tabela antiga, vazia) tinha `UNIQUE (veiculo_id, data_checklist)`** — impedia Retirada e Devolução no mesmo dia. Removida em 21/10/2026 (`ALTER TABLE ... DROP CONSTRAINT` funciona via MCP; o que trava é `DROP TABLE`/`DROP POLICY`).
7. **`DELETE` direto em `storage.objects` via MCP** pede confirmação e falhou ("Invalid or expired requestState"); além disso apagar a linha não apaga o arquivo físico. Arquivo de Storage se remove pelo painel do Supabase (Storage) ou pela API de Storage, não por SQL.

## Schema / banco de dados

Schema `frota` no Postgres do Supabase (migration fundacional em `claude/schema-fundacao-painel-gestao-2026-10-09.sql` no projeto Claude — não reproduzida aqui por completo, consultar lá ou direto no Supabase). Estrutura:

- **Núcleo:** `hubs`, `fornecedores`, `motoristas`, `veiculos`, `contratos` (+ view `v_contratos_vencendo`, `v_cadastro_frota`, `v_pool_km_contrato` para franquia de km em modo pool).
- **Utilização:** `rotas_realizadas`, `planejamento_picos`.
- **Manutenção:** `oficinas` (com `telefone`, `endereco`, `cnpj` — CNPJ salvo só com dígitos; adicionados em 21/10/2026), `ordens_servico` (enum `status_os` é um fluxo de fases: `agendada` → `aguardando_agendamento` → `aguardando_orcamento` → `em_execucao` → `aguardando_peca` → `aguardando_pagamento` → `concluida`/`cancelada` — valores antigos do enum como `aberta`/`em_reparo` ainda existem no tipo Postgres por não poderem ser removidos, mas não são mais usados em lugar nenhum), `os_pecas`, `os_anexos` (+ bucket Storage privado `os-anexos`), `checklist_padrao_tipo`, `os_checklist_itens` (checklist de *serviço* dentro da OS — não confundir com o checklist de veículo abaixo), `revisoes_preventivas` + views de SLA/ranking.
- **Checklist de veículo (desde 21/10/2026):**
  - `checklist_itens_catalogo` — itens por grupo, com `tipos` (`retirada`/`devolucao`/`inspecao_tecnica`), `severidade_padrao`, `subtipos` (ex. luz do painel: Injeção/Óleo/Bateria/ABS/Outra) e `combustiveis` (null = todos; ex. óleo do motor só `combustao,hibrido`, cabo de recarga só `eletrico,hibrido`). Incluir item novo = inserir linha, sem mexer em código. Retirada/Devolução: 8 itens em 4 grupos (vindos do Pipefy); Inspeção técnica: 33 itens em 7 grupos (lista aprovada pelo Jefferson).
  - `checklists` — tabela antiga reaproveitada com colunas novas (`tipo`, `hub_id`, `km`, `nivel_combustivel`, `bateria_pct`, `colaborador_matricula`, `colaborador_nome`, `preenchido_por` = auth.uid do auxiliar ou null p/ motorista, `status` rascunho/enviado, `resultado` ok/atencao/reparo_necessario/urgente, `qtd_anomalias_novas`, `enviado_em`). Colunas legadas `avarias_encontradas`, `pipefy_card_id`, `realizado`, `avaria_critica` continuam lá.
  - `checklist_grupos` (resposta por grupo, `tem_anomalia` derivado no servidor), `checklist_anomalias`, `checklist_fotos` (+ bucket privado `checklist-fotos`, caminho `{placa}/{checklist_id}/{arquivo}.jpg`, limite 5 MB, só imagens).
  - **Modelo das anomalias:** `nova = true` é a anomalia "raiz", com ciclo de vida (`status` aberta → em_reparo → resolvida/descartada, `resolvida_em`, `resolvida_por` preenchido por trigger com auth.uid; null = resolvida por um checklist com "não existe mais"). `nova = false` é uma *confirmação* num checklist posterior (`origem_anomalia_id` aponta pra raiz, `confirmacao` = `continua`/`nao_existe`). `veiculo_id` da anomalia é preenchido por trigger a partir do checklist. `os_id` existe mas ainda não é usado.
  - Funções: `finalizar_checklist(id)` (valida grupo com problema sem anomalia, **anomalia nova sem foto**, fotos fixas painel/frontal/traseira **só na Inspeção técnica**; aplica "não existe mais"; calcula `resultado` pela pior anomalia aberta do veículo) e `registrar_checklist(payload jsonb, preenchido_por, motorista_id)` (grava tudo numa transação, confere que cada foto existe no bucket e pertence ao checklist, chama `finalizar_checklist`; **idempotente** por id — reenvio devolve o resultado já gravado). `registrar_checklist` e `buscar_colaborador(matricula)` só podem ser chamadas por `service_role`.
  - Views (`security_invoker`): `v_qualidade_frota` (por veículo ativo: último checklist + contagem de anomalias abertas por severidade) e `v_anomalias_abertas` (raízes abertas/em reparo, com item, quem reportou, tipo do checklist e caminho da 1ª foto).
  - `usuarios_perfil.matricula` (única quando preenchida) — matrícula de auxiliares de frota, que não estão em `motoristas`.
  - **E-mail de alerta (fase 4, no ar desde 21/10/2026):** gatilho `checklist_alerta` (AFTER UPDATE OF status em `checklists`) chama via `pg_net` a Edge Function **`alerta-checklist`** quando o checklist vira `enviado` com `qtd_anomalias_novas > 0`. A função manda **1 e-mail por checklist** para **frota@beepsaude.com.br** (env `ALERTA_PARA` sobrescreve) por SMTP `smtp.gmail.com:465` (Edge Functions bloqueiam 25/587; lib denomailer — o `close()` dela não devolve Promise, não usar `.catch` nele). Conteúdo: placa, modelo, hub, tipo, quem preencheu, km/energia, resultado e cada anomalia nova (severidade, item, grupo, descrição) com link assinado da foto válido 7 dias; assunto com `[URGENTE]` se houver crítica. Anomalias já descartadas não entram (se todas foram descartadas, `alerta_status = 'ignorado'`). Controle em `checklists.alerta_status` (enviado/ignorado/erro), `alerta_enviado_em`, `alerta_erro`, `alerta_tentativas`, `alerta_reservado_em`; `reservar_alerta_checklist(id)` impede e-mail duplicado; cron **`alerta-checklist-pendentes`** (a cada 15 min) reenvia erros/pendentes das últimas 48h, até 5 tentativas. Autenticação: header `x-automation-key` validado por `verificar_chave_checklist()` contra o segredo `automation_secret_checklist` do Vault (para testar, chamar via `net.http_post` no SQL lendo o Vault, assim a chave não aparece no chat; resposta em `net._http_response`). Modos: `checklist`, `pendentes`, `teste` (manda para o próprio `SMTP_USER` com `[TESTE]`, sem marcar nada) e `diagnostico`. **Anomalia crítica só alerta por e-mail** — não marca o veículo indisponível nem abre OS (decisão do Jefferson).
- **Multas:** `multas` (muitos campos de fluxo: identificação, valores, prazos, pessoas/liderança, status) + view `v_multas_detalhe`.
- **Financeiro:** `categorias_custo`, `notas_fiscais` + view `v_fornecedores_nota_atrasada`.
- **Carros Elétricos:** `recargas_eletricas`, `telemetria_diaria`, `parametros_combustao_equivalente`.
- **Controle de acesso:** `usuarios_perfil` com `papel` (admin/operador/visualizador) + `modulos_visualizacao` e `modulos_operador` (arrays de texto). Função `frota.posso_ver(modulo)` (security definer) decide RLS de SELECT por módulo; admin vê tudo. Para o checklist há `posso_ver_checklist()` (módulo `checklist` **ou** `manutencao`) e `posso_editar_checklist()` (admin, ou operador com `checklist`/`manutencao`); quem vê checklist também tem SELECT em `veiculos` e `hubs` (policies `visualizar_veiculos_checklist`/`visualizar_hubs_checklist`, necessárias porque as views são `security_invoker`). Todas as tabelas do schema têm RLS habilitado. Views importantes usam `security_invoker = true` para herdar o RLS do usuário logado, não do dono da view — seguir esse padrão em views novas.

### Qualidade de dados — padrões para ficar de olho em novos imports
- Valores em R$ às vezes vêm como **texto** em vez de número (ex. `"R$ 1.160,00"`) — normalizar antes de inserir.
- Erros de fórmula do Excel (`#VALUE!`, `#REF!`) aparecem em imports — tratar como NULL, não travar o import.
- CPFs/placas duplicados por recadastro — preferir o registro com mais campos preenchidos, não o mais recente por padrão.

## Convenções

- **PII de motoristas é sensível** (CPF, RG, CNH, data de nascimento, senha de abastecimento): a tabela `frota.motoristas` só pode ser lida por `admin`. Para telas que só precisam listar/selecionar um motorista (ex. formulário de Multas), usar a view `frota.v_motoristas_basico` (sem dados sensíveis), nunca a tabela bruta. **Nunca armazenar link direto para foto/scan de CNH de terceiros** (links assinados do Pipefy expiram e, enquanto vivos, dão acesso à imagem do documento) — se precisar persistir o documento, subir pro Storage do Supabase com a mesma regra de acesso restrito a admin.
- Botões "+ Novo [registro]" ficam no topo do card, em destaque (não no fim da lista).
- Modais de criar/editar são compartilhados (mesmo formulário, título e texto do botão mudam, um campo oculto guarda o id em modo edição); salvar faz `PATCH` filtrando por id quando é edição, `POST` quando é criação.
- Sessão: front-end precisa refrescar o `access_token` do Supabase antes de expirar (1h) — ver bug corrigido abaixo. Qualquer novo fluxo de autenticação deve manter `ensureFreshSession()` antes de chamadas REST.
- Para dar acesso de **auxiliar de frota**: em `usuarios_perfil`, `papel = 'operador'`, `'checklist'` em `modulos_operador` e `matricula` preenchida (assim ela vem pronta no `checklist.html` após o login).
- Fotos de buckets privados (`os-anexos`, `checklist-fotos`) nunca são salvas como link: o front gera URL assinada na hora, com o token do usuário logado.
- **Comandos SQL que alteram dados reais (UPDATE/DELETE) só depois de mostrar o comando exato ao Jefferson e ele aprovar**, sempre com `WHERE` por id. Testes de banco são feitos dentro de um bloco `DO` que termina em `raise exception` (rollback garantido) — não deixar dado de teste no banco. Prefira "descartar" (status) a apagar.
